## Server / client boundaries

- **`'use client'` at the top of a shared layout or a barrel file** → the whole subtree becomes a
  client bundle. Push the directive down to the leaf that needs interactivity.
- A hook (`useState`, `useEffect`, `useRef`, `useContext`) or a browser API in a component without
  `'use client'` → build error at best, subtle behaviour at worst.
- **Non-serializable prop passed from a server to a client component** (a function, a class
  instance, a `Date` in older versions, a `Symbol`) → runtime error. Pass primitives and plain
  objects.
- `'use server'` on a module whose exports are not all server actions; a server action without its
  own authorisation and input validation — it is a public HTTP endpoint (see `security.md`).
- A server-only module (with secrets, `fs`, a DB client) imported by a client component → guard
  with `server-only`.
- Context provider in a server component → providers are client components; the boundary belongs
  above them.
- An `async` client component → not supported.

## Hydration mismatches

Symptom: a hydration warning, then a full client re-render of the subtree — and, until it happens,
the wrong markup on screen. Causes to look for in the diff:

- `Date.now()`, `new Date()`, a locale-formatted date, `Math.random()`, a uuid generated during
  render.
- `typeof window !== 'undefined' ? a : b` in the returned JSX → deliberately renders two different
  trees.
- Reading `localStorage`, `matchMedia`, `navigator`, `window.innerWidth` during render.
- A value that depends on the timezone or the browser locale (`toLocaleString` with no explicit
  locale).
- Invalid HTML nesting that the browser repairs (`<div>` inside `<p>`, `<p>` inside `<p>`, a
  `<div>` inside `<tbody>`) → the parsed DOM does not match React's tree.
- Ids generated by a module-level counter → different sequences on server and client. `useId` is
  the fix.
- Extension- or third-party-injected DOM inside a hydrated container.
- A conditional based on a cookie/header read only on one side.

The correct patterns: render the server-safe value first and update in an effect; or
`useSyncExternalStore` with a `getServerSnapshot`; or a mounted flag when the content genuinely
cannot exist on the server (accepting the extra render).

## SSR-safe browser access

- Module-scope access to `window`/`document` → crashes the server import, not just the render.
- `useLayoutEffect` in a component rendered on the server → warning; use `useEffect`, or the
  isomorphic-effect pattern.
- Observers, media queries and event listeners set up in `useEffect` only.
- A library that touches the DOM at import time must be dynamically imported client-side.

## Data fetching in an RSC app

- Fetching in a client component what a server component could fetch → extra roundtrip plus a
  loading state that need not exist.
- Cache semantics stated explicitly (`cache`, `revalidate`, `no-store`) — an accidental full-route
  cache serves stale or, worse, another user's data. Anything user-specific must not be cached.
- Sequential awaits in a server component that could be `Promise.all`.
- Per-request data read outside the request scope (a module-level cache holding user data) → cross
  request leakage.
- No `Suspense` boundary around a slow segment, so nothing streams.
- `error.tsx` / `not-found.tsx` missing for a new route segment.

## Metadata, images and routing

- New route without metadata (title, description) where the project sets it elsewhere.
- Raw `<img>` where the project uses the framework's image component (or the reverse, for a
  library that must stay framework-free).
- Client-side navigation replaced by an `<a href>` full reload, or the reverse for an external
  link.
- Loading and error states for a new route.
- A redirect or rewrite added without checking the open-redirect risk (see `security.md`).

## Publishing a library: entry points

- `exports` map complete and ordered: `types` **before** `import`/`require`, a `default` fallback,
  and an entry for every documented import path (`./styles.css`, `./package.json`).
- `main`/`module`/`types` consistent with `exports` for older tooling.
- `files` allowlist covers `dist` and nothing else — no sources, no fixtures, no `.map` unless
  intended. Verify with `npm pack --dry-run`.
- A new deep import path either added to `exports` or explicitly not supported.
- `sideEffects` accurate: `false` for a pure-ESM library, or an allowlist naming the CSS files.
  Wrong here means either broken CSS or dead code kept in consumers' bundles.

## Publishing a library: build output

- `'use client'` directives preserved in the emitted files when the components use hooks — bundlers
  strip directives unless configured. A build-verification script is the reliable guard; check it
  still covers new files.
- Generated `.d.ts` free of `any` leaks and of paths into `src`; relative imports carry the
  extension the module system needs.
- `react`/`react-dom` not bundled into the output.
- CSS emitted as a separate file, not injected by JS at import time (breaks SSR and CSP).
- Output format matches the `type` field; no CJS/ESM interop hazard (`require` of an ESM-only dep).
- The build actually runs in CI on the diff, and `dist` is not committed.

## Publishing a library: peer dependencies

- Support range in `peerDependencies` (for example `^17 || ^18 || ^19`) is the **hard constraint**
  on every API the code may use: `forwardRef` cannot be dropped, `useId`/`useSyncExternalStore`
  need ≥18, `use`/`useActionState`/ref-callback cleanup need 19 (see `react-correctness.md`).
  Using a newer API without widening the floor is a concern, not a suggestion.
- Narrowing the range is a breaking change; widening it needs a test or CI matrix that proves it.
- A runtime dependency that should be a peer (React, a design system), or a peer that should be a
  regular dependency.
- `peerDependenciesMeta.optional` where the import is unconditional.

## Release hygiene

- Public behaviour change with no changelog entry, when the project keeps one.
- Readme/docs/stories not updated for a new or renamed prop.
- A commit message that does not match the convention the repo enforces (commitlint,
  release-please) → the release automation derives the version from it, so a `fix:` for a breaking
  change ships a patch that breaks consumers.
- A new public export with no test and no story.
